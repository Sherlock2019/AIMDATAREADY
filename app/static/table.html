Is this data fit for this AI task, for this user and this agent, right now?

Task Data Readiness is a gate that runs before an AI agent touches supply-chain data. It checks that the data a task needs is authorized, current, complete, traceable and covered by a valid contract. Then it either releases only the authorized data, or explains exactly what is missing, why, and how to fix it.

What it is

A deterministic readiness engine with a guided workflow. Every AI task (compare stock, recommend a transfer, propose purchase orders, answer a policy question…) has a versioned, approved Data Readiness Profile: which data it needs and the rules that data must meet. The engine checks the actual data against that profile and returns READY, READY WITH WARNINGS or BLOCKED, with evidence for every check.

Why: the problem it solves

AI agents answer confidently even when their data is wrong for the job:

  • stale stock levels, so the agent recommends the wrong transfer
  • missing warehouses, lanes or periods, so the plan is incomplete
  • unknown units, codes or duplicate rows, so the numbers are wrong
  • data the user may not see (e.g. supplier prices) leaking through the agent
  • expired or superseded contracts quoted as if they were current

Generic data-quality tools check a dataset in general. This gate checks fitness for this task, this user and this agent at the moment of use.

How to use it

  1. Pick a user role, then a task that role may request.
  2. Read 3 Authorized data (allowed vs required) and 4 the readiness profile.
  3. Choose a data set. It does not say whether it is faulty; the checks find out.
  4. Click Run checks: every metric shows its value, status, fix and root cause.
  5. If BLOCKED: Propose fixes (mock agent or Claude), then Approve & apply. The engine re-checks. Fixes you may not approve: click Request approval; the approver finds them in Approval requests for you when they open the page as their role.
  6. If READY: each data set that passed is certified and published as a new version, ingested into the RAG index, and the agent reads only that certified data (ask it questions in the search box).
How AI readiness is assessed: every check the gate runs
01Role → task → profile

A role can request only its own tasks. Each task has exactly one approved, versioned profile. The engine never falls back to a weaker profile.

roles.yaml · tasks.yaml
02Access: user and agent

Checked separately for the user and the agent, at data-set, row (warehouse), column (e.g. supplier prices) and purpose level. Restricted data sets are not even named.

ACL per role · catalog permitted agents
03Catalog and contract

One file per data set holds the owner, steward, source, definitions, classification, schema, quality rules and SLAs. It is validated against the official standard.

ODCS v3.1.0 · JSON Schema validation
04Freshness

Source event time is compared with the task's own limit: inventory ≤ 2 h for a transfer, but 48 h is fine for a weekly report.

profile override · contract SLA latency
05Coverage

The rows must cover the requested product, warehouses, transfer lane and planning period. A missing partition blocks the task.

task context vs actual rows
06Quality

Required values, allowed codes and units, ISO dates, non-negative quantities and duplicate keys, checked only on the rows this task uses.

contract quality rules
07Provenance and lineage

Source system, snapshot version and ingestion time. Every extract, check, fix and retrieval is recorded as a standard lineage event.

OpenLineage events
08Documents and secure search

Only approved, currently valid documents count. Search results are filtered inside the vector query by the user's document groups, with citations.

Chroma · local embeddings · ACL filter
09Root cause

Each failing metric gets a root cause worked out from measured evidence (e.g. "uom contains 'KG', not allowed"), never guessed.

check evidence · offending values
10Fix proposals

Fixes come only from an allow-list: reload from the SAP source of record, the steward registry, or a lossless transform. Proposed by the mock agent or by Claude.

allow-listed actions · Claude optional
11Human approval loop

Only the domain owner may approve a fix; agents never approve. Approved fixes become upstream rules, so the next extraction is cleaner.

per-domain approvers · round history
12Use-time gate and evidence

The gate re-checks just before data is released, then hands the agent only permitted rows and columns. Each run gets an evaluation id, timings and an audit record.

re-check · audit log · metrics
READY every mandatory check passes: data is released READY WITH WARNINGS only optional data has issues BLOCKED a mandatory check failed or is unknown: nothing is released The role is a demo selector, not authentication.
